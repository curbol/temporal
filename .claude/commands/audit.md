# Audit

Deep review of the Temporal codebase: a hardware repo that builds a 36-42 key
split ergonomic keyboard from a single Ergogen config into PCBs, plates,
gerbers, JLCPCB assembly files, a ZMK physical layout, and 3D-printable cases.
Reviews everything by default. If the user provides a scope (e.g. "the JLCPCB
assembly generation" or "the post-processing scripts"), narrow to those areas.

Scope: $ARGUMENTS

## Step 2: Run baseline checks

Run these first. Proceed with the audit either way, since area findings may
explain a failure or reveal it as pre-existing. Report any failure as Tier 1,
ahead of new findings. Do not re-decide in prose what these commands decide:
if the formatter is clean, formatting is not a finding.

```bash
# The repo's own verification target, and what CI runs (~95s).
# It writes only to ergogen/output/ and temp dirs; a shell trap snapshots and
# restores temporal.json, jlcpcb/, and every .kicad_pro / .kicad_dru around the
# reproducibility check (Makefile:209-221), so it is safe with a dirty tree.
# Covers, in order: node --check on every script and footprint; py_compile on
# every scripts/*.py; bash -n on copy_pcb_if_missing.sh; a YAML parse of both
# config files; eslint; that ergogen/config.yaml still builds; that every
# committed board passes DRC at error severity; that no silkscreen face was
# substituted at export and every board naming a face embeds its own font;
# that the pours in pcbs/ still match the current custom DRC rules; that
# temporal.json, jlcpcb/, the .kicad_dru files and the config-owned subtrees
# of the .kicad_pro files all reproduce from their sources; and that every
# gerber zip re-exports byte-identical to the board in pcbs/, modulo the
# timestamp and tool-version lines.
make check

# Individual stages, when a make check failure needs isolating:
npm run --silent lint
node scripts/check_zone_fills.js
node scripts/check_kicad_pro.js <snapshot-dir>   # only meaningful inside make check
```

Not in the block: `npm audit --omit=dev` needs network, so run it separately
and report what it says rather than assuming. `make gen` and `make convert`
take minutes, run `make clean` first, and rewrite hundreds of committed binary
files; never run them as part of an audit. `make deps` clones a plugin from
GitHub and installs system packages; it needs network and sudo.

`make check` needs `kicad-cli`, an interpreter that can `import pcbnew`,
`unzip` (for the gerber comparison) and, on a headless machine, an X server
for the `wx.App` the pcbnew bindings construct. CI supplies the last with
`xvfb-run`.

A green `make check` establishes that the sources parse and lint, that the
config builds, that the boards are DRC-clean at error severity and carry their
own fonts, that the pours are current, and that every committed derived
artifact reproduces. It says nothing about whether the geometry is *correct*,
whether the STLs are manifold (no mesh checker is installed), whether any
script's regex still matches what the current Ergogen version emits, or
whether the parts of a `.kicad_pro` outside `check_kicad_pro.js`'s
`OWNED_PATHS` are what the config intends. Judgment has to cover all of that.

DRC *warnings* are expected and are not findings on their own. Exactly two
classes appear today and both are known: `isolated_copper` on the plates, the
back plates and the MCU cover, because their decorative pours connect to
nothing; and `text_thickness` on the three boards carrying silkscreen text
(`temporal`, `top_plate_38`, `top_plate_42`), because KiCad measures the
TrueType glyph outline rather than the `thickness` parameter, so curve joins
read below the floor. Both were reviewed and accepted. Errors are what matter,
and there are none.

- The full list of files in its area, not a diff.

- The review criteria below that apply to its area, plus the core invariants,

Tell sub-agents to read entire files rather than scanning for patterns.
Finding a real issue requires the surrounding context. Where a package
documents its own contract, hold the code to that contract.

### Priority tiers

Tier by consequence, not by category. The categories under each tier are
examples, not the definition.

**Tier 1 (must fix):** produces behavior a user or the data can observe as
wrong, or violates a core invariant. Bugs, races, corrupt or non-atomic
writes, swallowed errors that hide a failure, layer violations.

**Tier 2 (should fix):** correct today, but the next change in this area is
likely to break it, or a real invariant has no test. Significant duplication,
resource leaks, API shapes that invite misuse, meaningful refactors.

**Tier 3 (consider):** removes something concrete. If you cannot name what it
removes, leave it out.

### The finding gate

Every finding must name its failure scenario: the input, call sequence, or
state that produces the wrong outcome. "This could race" is not a finding.
"Two concurrent writes both read before either writes, so the second save
clobbers the first" is.

A finding that cannot name a trigger is dropped, not downgraded. Report file
and line, what goes wrong, and a fix specific enough to act on.

In a hardware repo the observable wrong outcome is usually physical: a board
that will not assemble, a case that will not fit, a gerber that a fab will
reject, a BOM that orders the wrong count. Prefer findings you can tie to one
of those.

### Review criteria

**Core invariants (hard rules, violations are Tier 1)**

These are the contracts the whole build rests on. See `CLAUDE.md`, the header
comment of `ergogen/config.yaml` (lines 1-11), `pcbs/temporal/README.md`,
`cases/README.md`, and the module docstrings of `scripts/drc_rules.js`
(lines 2-7), `scripts/kicad_config.js` (1-6), `scripts/ergogen_config.js`
(1-5), `scripts/check_kicad_pro.js` (2-9),
`scripts/fix_silkscreen_width.js` (2-18) and `scripts/embed_fonts.py` (2-19).

1. **`ergogen/config.yaml` is the only place geometry is authored.** Every
   dimension, offset, and outline in a shipped artifact traces back to it;
   generated `.kicad_pcb`, `.jscad`, and `.stl` files are never hand-edited to
   change geometry. `units:` (lines 24-193) holds every tuning constant by
   name, so a dimension change is a one-line edit at the top. Where a script
   needs one of those numbers it reads it through `unit()`
   (`scripts/ergogen_config.js:43-56`) rather than retyping it.
   *Violation shape:* a numeric literal in a `scripts/*.js` or `*.py` body
   that determines board or case geometry rather than KiCad's file format; an
   `outlines:` / `cases:` entry repeating a value that a `units:` name already
   holds, so the "one-line edit at the top" promise no longer holds.
   *Check:* grep the scripts for bare decimal literals and classify each as
   format constant or geometry. The known borderline cases are
   `add_ground_planes.js:58` and `:229` (a 2.0mm zone margin, passed as a
   default and repeated at the call site), `fix_edge_cuts.js:13`
   (`MIN_SEGMENT_LENGTH`) and `generate_layout.js:148` (the 2.02 half-to-half
   gap); confirm whether any *new* ones have appeared. The literals in
   `setup_kicad_project.js`'s `getBaseProjectStructure` (lines 21-287) are a
   different case: see invariant 5.

2. **The post-processing order in `Makefile:96-106` is load-bearing.** Each
   step mutates the `.kicad_pcb` files in place and assumes its predecessors
   ran. Specifically: `create_text_keepouts.js` must precede the pour; via
   stitching must precede zone filling, because placing vias invalidates
   existing fills; a board's `.kicad_dru` must exist before anything fills its
   zones, because the zone filler honours those rules; `embed_fonts.js` must
   run after every step that could add text; and `copy_pcb_if_missing.sh` must
   run after all of it, because whatever it copies is what `pcbs/` keeps.
   *Violation shape:* a call to `fill_zones.py` or `pcbnew.ZONE_FILLER`
   reachable without `writeDrcRules` having run for that board; a new step
   inserted into `Makefile:96-106` outside its dependency position; a derived
   board written with fills copied from a source whose rules differ.
   *Check:* `scripts/fill_zones.js:40-48` (rules written per board, then
   filled); `scripts/drc_rules.js:33-49`, noting that it *removes* the
   `.kicad_dru` when the rule list is empty (`:40-43`);
   `scripts/create_stealth_variants.js:158`;
   `scripts/setup_kicad_project.js:433`; the step ordering in
   `Makefile:96-106`.
   `fix_silkscreen_width.js` is the one step whose ordering constraint has
   *weakened*: both its widening pass (`:76-106`) and its `residualStrokes`
   backstop (`:140-177`) now walk balanced s-expressions, the backstop from
   each stroke outward via `enclosingBlockStart` (`:114-130`) so it does not
   share the forward scan's opening-token regex. Confirm the two really are
   independent, since the pass asserts its own coverage with them.

3. **`pcbs/temporal/temporal.kicad_pcb` is never overwritten by the build.**
   It is hand-routed in KiCad and the manual routing cannot be regenerated.
   Only its `.kicad_pro` and `.kicad_dru` are rewritten.
   *Violation shape:* any write to `pcbs/temporal/temporal.kicad_pcb` without
   an existence guard; a `pcbs/**` glob that copies Ergogen output over it; a
   clean target that removes the directory; a `pcbnew.SaveBoard` reachable
   with a path under `pcbs/`.
   *Check:* `scripts/copy_pcb_if_missing.sh:25` (the `[ ! -f ]` guard) and
   `Makefile:273` (the `! -name temporal` exclusion in `clean`). Then grep
   every script for writes whose path can resolve under `pcbs/temporal/`.
   Note that `check_zone_fills.py` deliberately refills in memory and writes
   nothing back (`:9-13`, `:63-65`); confirm that is still true, and that the
   gerber comparison at `Makefile:239-265` only ever exports to `$TMP`.

4. **Naming encodes key count, kickstand, and handedness, and nothing else.**
   A leading `_` marks an Ergogen-internal name that is never exported.
   `_left` is generated directly; `_m_right` is the mirror source that
   `convert_jscad.js` renames and mirrors into the right-hand STL. The
   `_m_right` suffix never survives into `cases/`. Exported half-cases are
   named `temporal_<38|42>[_kickstand]_<left|m_right>` and land at
   `cases/<count>/[kickstand_]<hand>.stl`; the per-count `top_plate` lands at
   `cases/<count>/top_plate.stl` and the shared `mcu_cover` is the one part
   that stays at the top of `cases/`. PCB variants keep the flat suffix form
   (`top_plate_42_stealth`).
   *Violation shape:* a file in `cases/` matching `*_m_right*`; an exported
   `cases:` key beginning with `_`; an `_m_right` case with no `_left`
   counterpart, or one whose parameters differ beyond the mirror; an exported
   case key that `outputRelPath` does not recognise, which silently lands the
   STL flat at the top of `cases/`; a switch generation or mounting token
   creeping back into a case name, which would mean the single case has been
   split again.
   *Check:* `find cases -name '*_m_right*'` must return nothing;
   `scripts/convert_jscad.js:45-61` (`outputRelPath`, whose two regexes are
   the whole mapping, with the unmatched fallthrough at `:60`), `:88` and
   `:128` (the mirror). Pair every `_left` against its `_m_right` in the
   `cases:` section of `ergogen/config.yaml`. The current state is 42 `cases:`
   keys, 11 of them exported, producing 11 STLs: two counts times
   plain-or-kickstand times two hands, plus two `top_plate` and one
   `mcu_cover`. The kickstand variants compose the already-derived case rather
   than repeating its subtractions.

   Related: every cutout in the case floor is blind, because
   `bottom_thickness` is `socket_depth + floor_skin` (`ergogen/config.yaml:173`,
   2.35mm) and nothing on the back of the PCB reaches deeper than the socket.
   *Violation shape:* a `cases:` block whose `extrude` is `bottom_thickness`
   for anything but the shell or the kickstand, which would punch a hole
   through the bottom face.
   *Check:* the bottom face of a built half-case has exactly two boundary
   loops, the outer perimeter and the MCU-area opening. More than that means a
   pocket broke through. `docs/bom.md:91-94` and `cases/README.md` both state
   the solid-bottom claim to builders, so a regression here also makes the
   docs wrong.

5. **`scripts/kicad_config.yaml` owns the tuning values, and
   `scripts/kicad_config.js` plus `scripts/ergogen_config.js` are the only
   readers of the two config files.** The YAML owns net classes, design rules,
   custom DRC rules, zone and via-stitching parameters, keepout text patterns,
   and the JLCPCB part numbers plus embedded-resistor positions. Adding an
   assembly part or changing a trace width is a config edit, not a code edit.
   `kicad_config.js:22-70` (`applyErgogenUnits`) fills the net class track and
   via geometry and the silkscreen pen in from `ergogen/config.yaml`'s
   `copper_*` and `silk_line_width` units, so those numbers are typed once;
   `ergogen_config.js:39-41` and `:58-82` supply `pcbNames()` and
   `ergogenOutputPcbs()`, so no script repeats the board list or the "has the
   build run" preamble.
   *Violation shape:* any of those categories appearing as a literal in a
   `.js` or `.py` body; a script calling `yaml.load` on either config path
   directly instead of going through the two modules; a hardcoded board list;
   a `?? <literal>` fallback in a script that disagrees with the value the
   YAML actually sets, so the YAML looks authoritative while the code silently
   wins; a key `setup_kicad_project.js` writes into a `.kicad_pro` that
   `check_kicad_pro.js`'s `OWNED_PATHS` does not compare, so a drift in it
   passes `make check`.
   *Check:* `grep -rn "yaml.load" scripts/` should return only
   `kicad_config.js:83`, `ergogen_config.js:27`, and `generate_layout.js:40`
   (which parses Ergogen's `points.yaml` output, not a config file). The
   design-rule and board-default fallbacks that used to disagree with the YAML
   are gone: `setup_kicad_project.js:350-358` (`required`) exits when a key
   listed in `DESIGN_RULE_KEYS` (`:323-336`) or `BOARD_DEFAULT_KEYS`
   (`:338-348`) is missing, and the matching literals in
   `getBaseProjectStructure` (e.g. `silk_line_width: 0.1` at `:65`,
   `silk_text_thickness: 0.1` at `:69`) are placeholders overwritten on every
   write. Confirm that still holds: a key dropped from either list would leave
   its placeholder in the file. The remaining live `??` literals are the net
   class geometry in `createNetClass` (`:300-313`), which `applyErgogenUnits`
   supplies for `track_width`, `via_diameter` and `via_drill` but not for
   `clearance`, `diff_pair_*` or `microvia_*`. `OWNED_PATHS`
   (`check_kicad_pro.js:14-19`) now covers all four subtrees
   `applyDefaultsToProject` writes (`:361-404`); what it does not cover is the
   rest of the skeleton, written once at creation and never compared again:
   `board.design_settings.rule_severities` (`:80`), `teardrop_options`,
   `teardrop_parameters`, `track_widths`, `tuning_pattern_settings`,
   `via_dimensions`, `zones_allow_external_fillets`, and the `pcbnew` and
   `schematic` sections. The remaining hardcoded list is `LAYERS_TO_PROCESS`
   at `scripts/create_text_keepouts.js:16`, mirrored by `SILKSCREEN_LAYERS` at
   `fix_silkscreen_width.js:23` and `create_stealth_variants.js:20`.

6. **Every side-bearing footprint on `pcbs.temporal` is `reversible: true`.**
   The board is reversible: one PCB serves as the left hand or, flipped, the
   right. A footprint that renders on only one side breaks one hand, and
   `generate_jlcpcb_files.js:283-290` rejects the build outright if an
   assembly part is not on both copper layers, because the two CPL files
   differ by rotation alone. `findParentFootprints` (`:89-100`) enforces the
   same thing for the jumper resistors' parent footprints.
   *Violation shape:* a footprint entry under `pcbs.temporal.footprints` in
   `ergogen/config.yaml` that declares a side but omits `reversible: true`; a
   patched footprint whose `reversible` branch places pads, traces, or vias
   that its non-reversible branch does not, or vice versa.
   *Check:* every `what: ceoloide/...` under `pcbs.temporal` (lines 1570-1770)
   either sets `reversible: true` or is `mounting_hole_npth`, which has no
   side. Ten reversible footprints and eight mounting holes is the current
   state.

7. **The KiCad 10 compatibility shims stay in place.** The installed toolchain
   is KiCad 10, while the ViaStitching plugin and parts of the pcbnew API
   assume KiCad 9 or earlier. Each shim has a comment saying why.
   *Violation shape:* a shim removed or bypassed; a new `pcbnew` call written
   against a pre-10 signature; a version comparison that compares the version
   string lexicographically, which sorts `"10.0.5"` below `"7"`.
   *Check:* `scripts/via_stitching.py:38-42` (the `SwigPyIterator.next` shim,
   mirrored at `create_text_keepouts.py:21-24`), `:44-55` (the
   `GetBoardPolygonOutlines` arity shim), `:57-103` (the `_ComparableVersion`
   shim and the version-sorted plugin path at `:156-164`),
   `scripts/create_text_keepouts.py:125-129` (the `SetDoNotAllowZoneFills` /
   `SetDoNotAllowCopperPour` rename), and the two `sed` patches to
   `FillArea.py` at `Makefile:69-70`. Those patches are verified twice, and
   both verifications must cover both patches: `Makefile:71-79` greps the file
   after patching, and `via_stitching.py:175-186` re-reads
   `inspect.getsource(FillArea)` at import and refuses to run against an
   unpatched copy.

8. **Silkscreen is uniform, bold, and every board carries its own fonts.** One
   face (`"Maple Mono NF"`), bold, and every stroke at `units.silk_line_width`
   (`ergogen/config.yaml:65`, currently 0.16mm, above JLCPCB's 0.153mm
   minimum). KiCad addresses fonts by family plus bold/italic and every Maple
   Mono file reports `Maple Mono NF` as its first fontconfig family, so a
   weight-suffixed name like `"Maple Mono NF ExtraBold"` resolves to nothing
   and is silently substituted at export; naming the plain family and setting
   bold is the only way to reach `MapleMono-NF-Bold.ttf`. Because the fonts
   are embedded, what gets fabricated does not depend on the exporting
   machine.
   *Violation shape:* a `face:` or `label_font_face:` value that is not
   exactly `"Maple Mono NF"`; a silkscreen text item that omits `bold` /
   `label_font_bold`, or sets a weight through the face name instead; a text
   `thickness` or `label_font_thickness` that is a literal rather than
   `silk_line_width`; a step ordered after `embed_fonts.js` that saves the
   board and drops `(embedded_fonts yes)`; a stealth variant that strips text
   but leaves megabytes of unused embedded typeface behind.

## Step 5: Verify and widen

For every finding from an area agent or from the cross-cutting analysis:

1. **Verify it yourself.** Read the file and line. Confirm the trigger is
   real. Drop anything speculative, cosmetic, or already handled elsewhere.
2. **Widen it.** Grep or glob for the same pattern across the whole
   codebase and report every occurrence, not just the one an agent happened
   to open.
3. **Mechanize what widens.** If a class has many instances and a tool could
   decide it, report one automation proposal instead of N findings: enable the
   lint rule, add the check, add a guard test. Check the lint configuration
   first, since a rule that exists but is disabled or not wired into CI is
   the cheapest fix available.
4. **Drop non-actionable observations.** Anything amounting to "noting this
   but it is fine" comes out.
5. **Deduplicate.** Merge findings that different agents reached from
   different angles into one item.

On step 3, note where this repo already stands. `make check` runs in CI on
every push and decides parsing, linting, the config build, DRC at error
severity, font resolution and embedding, zone-fill currency, and the
reproducibility of `temporal.json`, `jlcpcb/`, the `.kicad_dru` files, the
config-owned subtrees of the `.kicad_pro` files, and the gerber zips. That
leaves lint and `make check` as the two homes for a new automation, and
`check` is usually the right one.

On the lint side, `eslint.config.js` has `no-unused-vars` and `no-undef` on.
Enabling ESLint's recommended set on top of them currently produces zero
additional findings across all 35 linted files, so it is free to adopt and
buys future coverage rather than fixing anything today; `@eslint/js` is not
currently a dependency, so the proposal costs one package. Say plainly whether
that is worth it rather than assuming either way.

On the `check` side, the gaps a mechanical check could close: nothing asserts
that a dimension the YAML owns has not been re-typed as a literal in a script
or a doc; nothing compares the `.kicad_pro` keys outside
`check_kicad_pro.js`'s `OWNED_PATHS`; nothing catches a post-processing step
that succeeded over an empty input set; and nothing regenerates the STLs, so
`cases/` can fall behind `ergogen/config.yaml` unnoticed (a full STL rebuild
is minutes, so any proposal here has to say what it would cost). Propose these
only if the findings actually justify them, and say how many findings each
subsumes.

## Step 6: Report

Present the report and stop. Do not fix anything, do not write findings to
memory, and do not leave a findings file behind: the human triages in the
session, and saved findings become confidently wrong context later.

Organize by tier, then by category within a tier. Within a tier, order by
value against effort.

Each finding gets:
- File path and line numbers
- The failure scenario: what goes wrong and what triggers it
- A fix specific enough to act on
- One entry per pattern, with all occurrences grouped under it

**Test quality findings** are a cohesive assessment per area, not a list of
files. "The syncer tests cover classify and dedup well but nothing exercises
the expired-session abort" beats "syncer_test.go:42: missing test".

**Refactor findings** include a sketch of the target structure, or at minimum
name the functions and types that would result.

**Automation proposals** name the rule or check, the config file it goes in,
and roughly how many current findings it subsumes.

An area with no findings says so. A short report on sound code is a successful
audit, not a lazy one. No nits, no cosmetic notes, no "just flagging this".
