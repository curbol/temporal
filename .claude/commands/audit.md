# Audit

Deep review of the Temporal codebase: a hardware repo that builds a 36-42 key
split ergonomic keyboard from a single Ergogen config into PCBs, plates,
gerbers, JLCPCB assembly files, a ZMK physical layout, and 3D-printable cases.
Reviews everything by default. If the user provides a scope (e.g. "the JLCPCB
assembly generation" or "the post-processing scripts"), narrow to those areas.

Scope: $ARGUMENTS

## Step 1: Determine scope

- **No arguments:** review `ergogen/config.yaml`; every file in `scripts/`
  (`.js`, `.py`, `.sh`, `kicad_config.yaml`); the `Makefile`; the locally
  patched footprints in `ergogen/footprints/ceoloide/`
  (`switch_choc_v1_v2.js`, `mcu_nice_nano.js`, `display_nice_view.js`,
  `battery_connector_jst_ph_2.js`, `power_switch_smd_side.js`,
  `reset_switch_smd_side.js`, `rotary_encoder_ec11_ec12.js`,
  `diode_tht_sod123.js`, `mounting_hole_npth.js`, `utility_text.js`); and the
  root-level `package.json`, `.gitignore`, `README.md`, `docs/bom.md`,
  `docs/build-guide.md`. Do not forget `scripts/convert_svg_to_footprint.js`
  and `scripts/drc_rules.js`, which the Makefile never invokes but which are
  still source.
- **With scope:** interpret the user's wording to identify which of the areas
  in Step 3 to review. When in doubt, include more rather than less.

Do not review: `node_modules/`; `ergogen/output/` (regenerated by every run
and gitignored); `cases/*.stl`, `gerbers/*.zip`, `jlcpcb/*.csv`,
`pcbs/*/pcb.png`, `temporal.json`, and `assets/preview.svg` (all generated
build artifacts, committed only so consumers can download them);
`pcbs/*/*.kicad_pcb` and `pcbs/*/*.kicad_pro` (generated, and in the case of
`pcbs/temporal/` hand-routed in KiCad rather than authored as text);
and `ergogen/footprints/ceoloide/brain.js`, `neuron.js`, and
`solar_system.js` (SVG artwork mechanically converted to footprints,
unreferenced by `ergogen/config.yaml` today). Where an exclusion is produced
by code in this repo, review the producer instead:
`scripts/convert_svg_to_footprint.js` for the artwork
footprints, `scripts/generate_jlcpcb_files.js` for `jlcpcb/`,
`scripts/generate_layout.js` for `temporal.json`, `scripts/convert_jscad.js`
for `cases/`, and `ergogen/config.yaml` for everything else.

## Step 2: Run baseline checks

Run these first. Proceed with the audit either way, since area findings may
explain a failure or reveal it as pre-existing. Report any failure as Tier 1,
ahead of new findings. Do not re-decide in prose what these commands decide:
if the formatter is clean, formatting is not a finding.

```bash
# Syntax and parse checks (instant)
for f in scripts/*.js ergogen/footprints/ceoloide/*.js; do node --check "$f" || echo "FAIL $f"; done
python3 -m py_compile scripts/via_stitching.py scripts/fill_zones.py
bash -n scripts/copy_pcb_if_missing.sh
node -e "const y=require('js-yaml'),f=require('fs');y.load(f.readFileSync('ergogen/config.yaml','utf8'));y.load(f.readFileSync('scripts/kicad_config.yaml','utf8'))"

# The config still builds (~5s, writes only to gitignored ergogen/output/)
npm run gen

# Every committed board passes DRC at error severity (~3s total)
for pcb in pcbs/*/*.kicad_pcb; do
  kicad-cli pcb drc --severity-error --exit-code-violations -o /dev/null "$pcb" >/dev/null \
    || echo "DRC ERRORS: $pcb"
done

# The committed derived artifacts still match what the source produces.
# Guarded so it never destroys uncommitted work, and restores what it wrote.
if git diff --quiet -- temporal.json jlcpcb/; then
  node scripts/generate_layout.js >/dev/null && git diff --exit-code --stat -- temporal.json || echo "temporal.json STALE"
  make assembly >/dev/null && git diff --exit-code --stat -- jlcpcb/ || echo "jlcpcb/ STALE"
  git checkout -- temporal.json jlcpcb/
else
  echo "SKIP reproducibility: uncommitted changes in temporal.json or jlcpcb/"
fi

npm audit --omit=dev
```

There is no test suite, no linter, and no CI in this repo, so a green baseline
means much less here than in a software repo. It establishes only that the
scripts parse, that `ergogen/config.yaml` still builds, that the committed
boards are DRC-clean at error severity, and that `temporal.json` and
`jlcpcb/` are reproducible from their sources. It says nothing about whether
the geometry is *correct*, whether the STLs are manifold (no mesh checker is
installed), whether the gerbers match the boards, or whether any script's
regex still matches what the current Ergogen version emits. Judgment has to
cover all of that.

Deliberately not in the block: `make gen` and `make convert` take minutes,
run `make clean` first, and rewrite hundreds of committed binary files. Never
run them as part of an audit. `make deps` clones a plugin from GitHub and
installs system packages; it needs network and sudo.

DRC warnings are expected and are not findings on their own: the plates carry
`isolated_copper` warnings because their decorative pours connect to nothing.
Errors are what matter.

## Step 3: Dispatch review sub-agents

Use `feature-dev:code-reviewer` sub-agents to review the scoped files. Split
by area so agents run in parallel:

- **Geometry source of truth** — `ergogen/config.yaml`. The single place all
  board, plate, and case geometry is authored, ordered `units` → `points` →
  `outlines` → `cases` → `pcbs`. What goes wrong here: a literal dimension
  written inline where a `units` name already holds the value, so a later
  one-line change misses it; a `_left` / `_m_right` pair that has silently
  diverged; the 38 and 42 variants of the same part drifting apart; an
  intermediate that lost its leading `_` and now leaks into output.

- **PCB post-processing pipeline** — `Makefile`, `scripts/fix_edge_cuts.js`,
  `scripts/add_ground_planes.js`, `scripts/create_text_keepouts.js`,
  `scripts/via_stitching.js`, `scripts/via_stitching.py`,
  `scripts/fill_zones.js`, `scripts/fill_zones.py`, `scripts/drc_rules.js`,
  `scripts/kicad_python.js`, `scripts/setup_kicad_project.js`,
  `scripts/create_stealth_variants.js`, `scripts/copy_pcb_if_missing.sh`,
  `scripts/kicad_config.yaml`. These mutate `.kicad_pcb` files in place, in a
  fixed order, mostly by regex over KiCad s-expressions. What goes wrong here:
  a regex that matches the wrong construct or the wrong occurrence; a step
  that assumes a predecessor already ran; an error path that logs and
  continues, leaving a half-processed board that later steps treat as good; a
  write that reaches the hand-routed board.

- **Derived artifacts and manufacturing outputs** —
  `scripts/generate_jlcpcb_files.js`, `scripts/generate_layout.js`,
  `scripts/convert_jscad.js`, `scripts/convert_svg_to_footprint.js`, the
  `gerbers` / `assembly` / `convert` Makefile targets, `docs/bom.md`,
  `docs/build-guide.md`, `README.md`. These turn the source of truth into
  things a manufacturer or a user consumes, and a mistake here ships as a
  wrong physical object. What goes wrong: coordinate and rotation math;
  mirroring and left/right derivation; a hardcoded mapping table that has
  drifted from `points.zones`; documented quantities that no longer match the
  generated BOM.

- **Locally patched vendored footprints** —
  `ergogen/footprints/ceoloide/switch_choc_v1_v2.js`, `mcu_nice_nano.js`,
  `display_nice_view.js`, `battery_connector_jst_ph_2.js`,
  `power_switch_smd_side.js`, `reset_switch_smd_side.js`,
  `rotary_encoder_ec11_ec12.js`, `diode_tht_sod123.js`,
  `mounting_hole_npth.js`, `utility_text.js`. Vendored from ceoloide's library
  and patched locally for traces, vias, jumper resistor pads, choc v2 support,
  and KiCad 10 compatibility. What goes wrong: a patch applied to only one of
  the `reversible` code paths, so the left and right hands differ; pad or net
  names that no longer line up with the `column_net` / `row_net` values the
  config passes in; geometry added without a matching clearance, which only
  DRC on a board that actually uses that parameter combination would catch.

For each sub-agent, provide:
- The full list of files in its area, not a diff.
- The scope description from the user, if any, so it knows what to focus on.
- The review criteria below that apply to its area, plus the core invariants,
  which apply everywhere.

Tell sub-agents to read entire files rather than scanning for patterns.
Finding a real issue requires the surrounding context. Where a package
documents its own contract, hold the code to that contract.

### Priority tiers

Tier by consequence, not by category. The categories under each tier are
examples, not the definition.

**Tier 1 (must fix):** produces behavior a user or the data can observe as
wrong, or violates a core invariant. Bugs, races, corrupt or non-atomic
writes, swallowed errors that hide a failure, layer violations.

**Tier 2 (should fix):** correct today, but the next change in this area is
likely to break it, or a real invariant has no test. Significant duplication,
resource leaks, API shapes that invite misuse, meaningful refactors.

**Tier 3 (consider):** removes something concrete. If you cannot name what it
removes, leave it out.

### The finding gate

Every finding must name its failure scenario: the input, call sequence, or
state that produces the wrong outcome. "This could race" is not a finding.
"Two concurrent writes both read before either writes, so the second save
clobbers the first" is.

A finding that cannot name a trigger is dropped, not downgraded. Report file
and line, what goes wrong, and a fix specific enough to act on.

In a hardware repo the observable wrong outcome is usually physical: a board
that will not assemble, a case that will not fit, a gerber that a fab will
reject, a BOM that orders the wrong count. Prefer findings you can tie to one
of those.

### Review criteria

**Core invariants (hard rules, violations are Tier 1)**

These are the contracts the whole build rests on. See `CLAUDE.md`, the header
comment of `ergogen/config.yaml` (lines 1-13), `pcbs/temporal/README.md`, and
the docstring of `scripts/drc_rules.js` (lines 2-7).

1. **`ergogen/config.yaml` is the only place geometry is authored.** Every
   dimension, offset, and outline in a shipped artifact traces back to it;
   generated `.kicad_pcb`, `.jscad`, and `.stl` files are never hand-edited to
   change geometry.
   *Violation shape:* a numeric literal in a `scripts/*.js` or `*.py` body
   that determines board or case geometry rather than KiCad's file format; an
   `outlines:` / `cases:` entry repeating a value that a `units:` name already
   holds, so the "one-line edit at the top" promise no longer holds.
   *Check:* grep the scripts for bare decimal literals and classify each as
   format constant or geometry. The known borderline cases are
   `add_ground_planes.js:227` (a 2.0 mm zone margin) and `fix_edge_cuts.js:15`
   (`MIN_SEGMENT_LENGTH`); confirm whether any *new* ones have appeared.

2. **The post-processing order in `Makefile:73` is load-bearing.** Each step
   mutates the `.kicad_pcb` files in place and assumes its predecessors ran.
   In particular a board's `.kicad_dru` must exist before anything fills its
   zones, because the zone filler honours those rules, and via stitching must
   run before zone filling, because placing vias invalidates existing fills.
   *Violation shape:* a call to `fill_zones.py` or `pcbnew.ZONE_FILLER`
   reachable without `writeDrcRules` having run for that board; a new step
   inserted into `Makefile:73` outside its dependency position; a derived
   board written with fills copied from a source whose rules differ.
   *Check:* `scripts/fill_zones.js:63-65` (rules written, then filled);
   `scripts/create_stealth_variants.js:146`;
   `scripts/setup_kicad_project.js:458`; the step ordering in `Makefile:73`.

3. **`pcbs/temporal/temporal.kicad_pcb` is never overwritten by the build.**
   It is hand-routed in KiCad and the manual routing cannot be regenerated.
   Only its `.kicad_pro` and `.kicad_dru` are rewritten.
   *Violation shape:* any write to `pcbs/temporal/temporal.kicad_pcb` without
   an existence guard; a `pcbs/**` glob that copies Ergogen output over it; a
   clean target that removes the directory.
   *Check:* `scripts/copy_pcb_if_missing.sh:30` (the `[ ! -f ]` guard) and
   `Makefile:163` (the `! -name '$(TEMPORAL_DIR)'` exclusion, with
   `TEMPORAL_DIR := temporal` at `Makefile:8`). Then grep every script for
   writes whose path can resolve under `pcbs/temporal/`.

4. **Naming encodes generation and handedness.** A leading `_` marks an
   Ergogen-internal name that is never exported. `_left` is generated
   directly; `_m_right` is the mirror source that `convert_jscad.js` renames
   and mirrors into `<name>_right.stl`. The `_m_right` suffix never survives
   into `cases/`. Variants encode key count (`38` breakoff pinky, `42` full
   pinky) plus option suffixes (`socket`/`solder`, `kickstand`, `stealth`).
   *Violation shape:* a file in `cases/` matching `*_m_right*`; an exported
   `cases:` key beginning with `_`; an `_m_right` case with no `_left`
   counterpart, or one whose parameters differ beyond the mirror.
   *Check:* `ls cases/ | grep _m_right` must return nothing;
   `scripts/convert_jscad.js:63` and `:69-71`; pair every `_left` against its
   `_m_right` in the `cases:` section of `ergogen/config.yaml`.

5. **`scripts/kicad_config.yaml` owns the tuning values, not the script
   bodies.** Specifically: net classes, design rules, custom DRC rules, zone
   and via-stitching parameters, keepout text patterns, and the JLCPCB part
   numbers plus embedded-resistor positions. Adding an assembly part or
   changing a trace width is a config edit, not a code edit.
   *Violation shape:* any of those categories appearing as a literal in a
   `.js` or `.py` body; a `?? <literal>` fallback in a script that disagrees
   with the value the YAML actually sets, so the YAML looks authoritative
   while the code silently wins.
   *Check:* every `??` in `scripts/setup_kicad_project.js:333-458` against the
   corresponding key in `scripts/kicad_config.yaml`; the hardcoded `GAP_MM`
   and `LAYERS_TO_PROCESS` at `scripts/create_text_keepouts.js:17-18`; the
   hardcoded `SOURCE_PCBS` at `scripts/create_stealth_variants.js:13` and
   `PCB_FILES` at `scripts/copy_pcb_if_missing.sh:12-19`, both of which
   duplicate the `pcbs:` section of `ergogen/config.yaml`.

6. **Every side-bearing footprint on `pcbs.temporal` is `reversible: true`.**
   The board is reversible: one PCB serves as the left hand or, flipped, the
   right. A footprint that renders on only one side breaks one hand.
   *Violation shape:* a footprint entry under `pcbs.temporal.footprints` in
   `ergogen/config.yaml` that declares a side but omits `reversible: true`; a
   patched footprint whose `reversible` branch places pads, traces, or vias
   that its non-reversible branch does not, or vice versa.
   *Check:* every `what: ceoloide/...` under `pcbs.temporal` either sets
   `reversible: true` or is `mounting_hole_npth`, which has no side. Ten
   reversible footprints and eight mounting holes is the current state.

7. **The KiCad 10 compatibility shims stay in place.** The installed toolchain
   is KiCad 10, while the ViaStitching plugin and parts of the pcbnew API
   assume KiCad 9 or earlier. Three shims exist and each has a comment saying
   why.
   *Violation shape:* a shim removed or bypassed; a new `pcbnew` call written
   against a pre-10 signature; a version comparison that compares the version
   string lexicographically, which sorts `"10.0.5"` below `"7"`.
   *Check:* `scripts/via_stitching.py:38-49` (the `GetBoardPolygonOutlines`
   arity shim), `:51-87` (the `_ComparableVersion` shim),
   `scripts/create_text_keepouts.js:141-144` (the
   `SetDoNotAllowZoneFills` / `SetDoNotAllowCopperPour` rename), and the two
   `sed` patches to `FillArea.py` in `Makefile:30`.

**Write integrity**

- Every post-processing script reads a `.kicad_pcb`, edits a string, and
  writes it back to the same path with no temp file and no atomic rename. An
  interrupted or throwing write leaves a truncated board that the next step
  reads as valid. Assess whether this matters given the files are
  regenerable, and whether `pcbs/temporal/` is ever a target. Tier 2, Tier 1
  for anything that can truncate the hand-routed board.
- `scripts/create_text_keepouts.js:229-232` writes a temporary Python file
  into `scripts/` itself rather than a temp directory, and `:274-282` removes
  it in a `finally`. A crash between write and cleanup leaves
  `scripts/tmp_create_text_keepouts.py` in the working tree, untracked and
  not gitignored. Tier 2.
- `scripts/create_text_keepouts.js:269-273` catches every failure, logs it,
  and returns normally, so `make gen` continues with unprocessed boards and
  reports success. Compare against the other scripts, which `process.exit(1)`.
  Tier 1 if a silent failure here can ship a board whose silkscreen is buried
  under the pour.
- `scripts/fill_zones.js:25-28` and `scripts/via_stitching.js:65-68` log and
  continue per-file, then print a success count. Check whether a partial
  failure is distinguishable from success in the build output. Tier 2.

**Paths and portability**

- The `Makefile` branches on `uname -s` for `SED_I`, `KICAD_USER_DIR`, and the
  package installer, while `scripts/kicad_python.js` and
  `scripts/via_stitching.py:118-138` each carry their own platform switch with
  a different set of search paths. Verify the three agree about where KiCad
  and its plugins live on each platform, and flag paths that no longer exist
  for KiCad 10. Tier 2.
- `README.md` says KiCad v9 and lists Homebrew as a prerequisite, while the
  `Makefile` handles pacman on Linux and the scripts carry KiCad 10 shims.
  `README.md` also references `scripts/kicad_defaults.yaml`, which does not
  exist; the file is `scripts/kicad_config.yaml`. Tier 2, since a contributor
  follows these.
- `scripts/kicad_config.yaml:100-101` defines `pcb_settings.pad_to_mask_clearance`,
  which no script reads. Either wire it up or delete it. Tier 3.

**Cross-artifact consistency**

- The quantities in `docs/bom.md` must match what the build produces: diode
  count against the `switch_choc_v1_v2` footprint count on the board and
  against `jlcpcb/temporal_BOM.csv`; M2 insert and screw counts against the
  mounting holes and posts in `ergogen/config.yaml`. Tier 1 on a mismatch,
  since a user orders parts from this table.
- `docs/build-guide.md` describes jumper locations and key configurations that
  the config generates. Verify the described configurations (42/41/40 with the
  full pinky column, 38/37/36 with the breakoff) are the ones the `cases:` and
  `pcbs:` sections actually emit. Tier 2.

**Duplication and extraction**

- Repeated blocks (5 or more lines, similar structure) across files that
  should be a shared helper. Tier 2.
- Ignore trivial similarity: both call the same stdlib helper, both have an
  error check. Only flag duplication where extracting it measurably reduces
  the bug surface or eases a likely change.

Concretely: five scripts each open `scripts/kicad_config.yaml` with their own
near-identical loader (`add_ground_planes.js:18-33`, `drc_rules.js:16-27`,
`via_stitching.js:20-36`, `setup_kicad_project.js:23-35`,
`generate_jlcpcb_files.js:19-35`, `create_text_keepouts.js:15-16`), and four
repeat the same "does `ergogen/output/pcbs` exist, glob it, exit if empty"
preamble. `generate_jlcpcb_files.js:40-98` and `:103-139` are two copies of
the same footprint parser differing only in their filter.

**Refactoring opportunities**

- Code that grew incrementally and would benefit from restructuring now that
  its shape is clear: a function doing three things that should be three; a
  type that accumulated responsibilities; data flow that got indirect when a
  simpler path exists. Tier 2.
- Every suggestion must name a concrete improvement. It **removes** something
  (an indirection, a duplicated pattern, a coordination point, a way for two
  things to get out of sync), **enables** something (makes X testable,
  unblocks a use case, lets a change land in one place instead of N), or
  **generalizes meaningfully** (one shape replaces N near-duplicate variants).
  "Same behavior, different shape" does not qualify, however elegant. If you
  cannot name what improved, leave it out.

**Test quality (assess each suite as a whole, not test by test)**

This repo has no test suite and no test framework, and for most of it that is
the right call: the verification that matters is DRC on the generated boards
and a visual check in a slicer. Do not propose a test framework or unit tests
for the KiCad-mutating scripts.

Do assess whether the pure functions that carry real risk could be checked
cheaply and mechanically, and propose at most one such check where the payoff
is clear: the coordinate and rotation math in
`generate_jlcpcb_files.js:145-159` and `:297-321`, the mirror math in
`generate_layout.js:172-187`, and the s-expression block extraction in
`create_stealth_variants.js:20-44`. A guard that fails the build when
`generate_layout.js`'s column maps and `points.zones` disagree is worth more
than any number of unit tests, because that mismatch fails silently today.

- Significant production behavior with no test at all, especially the core
  invariants above and every branch of the logic named under Correctness.
  Tier 2.
- Clusters of overlapping tests that could consolidate into fewer, clearer
  cases. Tier 2.
- Tests asserting implementation details (internal call order, private
  fields) instead of observable behavior. They break on refactor for no
  value. Tier 2.
- Duplicated test setup or helpers that could be shared. Tier 2.
- Weak assertions (a count checked but not the values, the wrong field
  asserted). Tier 2 only where the weakness could mask a real bug.
- Do not suggest tests for trivial edge cases, for every possible nil input,
  or splitting working tests for purity. Fewer, stronger tests beat many
  fragile ones.

## Step 5: Verify and widen

For every finding from an area agent or from the cross-cutting analysis:

1. **Verify it yourself.** Read the file and line. Confirm the trigger is
   real. Drop anything speculative, cosmetic, or already handled elsewhere.
2. **Widen it.** Grep or glob for the same pattern across the whole
   codebase and report every occurrence, not just the one an agent happened
   to open.
3. **Mechanize what widens.** If a class has many instances and a tool could
   decide it, report one automation proposal instead of N findings: enable the
   lint rule, add the check, add a guard test. Check the lint configuration
   first, since a rule that exists but is disabled or not wired into CI is
   the cheapest fix available.
4. **Drop non-actionable observations.** Anything amounting to "noting this
   but it is fine" comes out.
5. **Deduplicate.** Merge findings that different agents reached from
   different angles into one item.

On step 3, this repo has no lint configuration and no CI at all, so the
cheapest available automation is different from the usual answer. In rough
order of payoff for what it would subsume: a `.github/workflows/` job running
the Step 2 baseline block on every push; an ESLint config with
`no-unused-vars` enabled, which subsumes several findings named under
Correctness; and a `make check` target so the baseline is runnable by name.
Propose these only if the findings actually justify them, and say how many
findings each subsumes.

## Step 6: Report

Present the report and stop. Do not fix anything, do not write findings to
memory, and do not leave a findings file behind: the human triages in the
session, and saved findings become confidently wrong context later.

Organize by tier, then by category within a tier. Within a tier, order by
value against effort.

Each finding gets:
- File path and line numbers
- The failure scenario: what goes wrong and what triggers it
- A fix specific enough to act on
- One entry per pattern, with all occurrences grouped under it

**Test quality findings** are a cohesive assessment per area, not a list of
files. "The syncer tests cover classify and dedup well but nothing exercises
the expired-session abort" beats "syncer_test.go:42: missing test".

**Refactor findings** include a sketch of the target structure, or at minimum
name the functions and types that would result.

**Automation proposals** name the rule or check, the config file it goes in,
and roughly how many current findings it subsumes.

An area with no findings says so. A short report on sound code is a successful
audit, not a lazy one. No nits, no cosmetic notes, no "just flagging this".
