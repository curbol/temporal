# Audit

Deep review of the Temporal codebase: a hardware repo that builds a 36-42 key
split ergonomic keyboard from a single Ergogen config into PCBs, plates,
gerbers, JLCPCB assembly files, a ZMK physical layout, and 3D-printable cases.
Reviews everything by default. If the user provides a scope (e.g. "the JLCPCB
assembly generation" or "the post-processing scripts"), narrow to those areas.

Scope: $ARGUMENTS

## Step 1: Determine scope

- **No arguments:** review `ergogen/config.yaml`; every file in `scripts/`
  (`.js`, `.py`, `.sh`, `kicad_config.yaml`); the `Makefile`;
  `eslint.config.js`; `.github/workflows/check.yml`; the locally patched
  footprints in `ergogen/footprints/ceoloide/`
  (`switch_choc_v1_v2.js`, `mcu_nice_nano.js`, `display_nice_view.js`,
  `battery_connector_jst_ph_2.js`, `power_switch_smd_side.js`,
  `reset_switch_smd_side.js`, `rotary_encoder_ec11_ec12.js`,
  `diode_tht_sod123.js`, `mounting_hole_npth.js`, `utility_text.js`); and the
  root-level `package.json`, `.gitignore`, `README.md`, `docs/bom.md`,
  `docs/build-guide.md`, `pcbs/temporal/README.md`. Do not forget
  `scripts/convert_svg_to_footprint.js`, which no `make` target invokes but
  which is still source.
- **With scope:** interpret the user's wording to identify which of the areas

(generated, and in the case of `pcbs/temporal/` hand-routed in KiCad rather

`neuron.js`, `solar_system.js`, `mounting_hole_plated.js` and
`utility_circle.js` (the first three are SVG artwork mechanically converted to

referenced by `ergogen/config.yaml` today, and CLAUDE.md says being
unreferenced is not a reason to delete them). Where an exclusion is produced
by code in this repo, review the producer instead:
`scripts/convert_svg_to_footprint.js` for the artwork footprints,
`scripts/generate_jlcpcb_files.js` for `jlcpcb/`,
`scripts/generate_layout.js` for `temporal.json`, `scripts/convert_jscad.js`
for `cases/`, `scripts/setup_kicad_project.js` and `scripts/drc_rules.js` for
the `.kicad_pro` and `.kicad_dru` files, and `ergogen/config.yaml` for
everything else.

## Step 2: Run baseline checks

Run these first. Proceed with the audit either way, since area findings may
explain a failure or reveal it as pre-existing. Report any failure as Tier 1,
ahead of new findings. Do not re-decide in prose what these commands decide:
if the formatter is clean, formatting is not a finding.

```bash
# The repo's own verification target, and what CI runs (~70s).
# It writes only to ergogen/output/, and snapshots and restores temporal.json
# and jlcpcb/ around the reproducibility check, so it is safe with a dirty tree.
# Covers, in order: node --check on every script and footprint; py_compile on
# every scripts/*.py; bash -n on copy_pcb_if_missing.sh; a YAML parse of both
# config files; eslint; that ergogen/config.yaml still builds; that every
# committed board passes DRC at error severity; that no silkscreen face was
# substituted at export and every board naming a face embeds its own font;
# that the pours in pcbs/ still match the current custom DRC rules; and that
# temporal.json and jlcpcb/ still reproduce from their sources.
make check

# Individual stages, when a make check failure needs isolating:
npm run --silent lint
node scripts/check_zone_fills.js
```

Not in the block: `npm audit --omit=dev` needs network, so run it separately
and report what it says rather than assuming. `make gen` and `make convert`
take minutes, run `make clean` first, and rewrite hundreds of committed binary
files; never run them as part of an audit. `make deps` clones a plugin from
GitHub and installs system packages; it needs network and sudo.

A green `make check` establishes that the sources parse and lint, that the
config builds, that the boards are DRC-clean at error severity and carry their
own fonts, that the pours are current, and that two derived artifacts
reproduce. It says nothing about whether the geometry is *correct*, whether
the STLs are manifold (no mesh checker is installed), whether the committed
gerbers still match the committed boards (nothing regenerates or diffs them),
or whether any script's regex still matches what the current Ergogen version
emits. Judgment has to cover all of that.

DRC *warnings* are expected and are not findings on their own. Two classes
appear today and both are known: `isolated_copper` on the plates and the MCU
cover, because their decorative pours connect to nothing; and
`text_thickness` on any board carrying silkscreen text, because KiCad measures
the TrueType glyph outline rather than the `thickness` parameter, so curve
joins read below the floor. Both were reviewed and accepted. Errors are what
matter.

Use `feature-dev:code-reviewer` sub-agents to review the scoped files. Split
by area so agents run in parallel:

- **Geometry source of truth** — `ergogen/config.yaml`. The single place all

  a `units` name already holds the value, so a later one-line change misses
  it; a `_left` / `_m_right` pair that has silently diverged; the 38 and 42
  variants of the same part drifting apart; an intermediate that lost its
  leading `_` and now leaks into output.

- **PCB post-processing pipeline** — `Makefile`, `scripts/kicad_config.js`,
  `scripts/ergogen_config.js`, `scripts/fix_edge_cuts.js`,
  `scripts/fix_silkscreen_width.js`, `scripts/add_ground_planes.js`,
  `scripts/create_text_keepouts.js`, `scripts/create_text_keepouts.py`,
  `scripts/via_stitching.js`, `scripts/via_stitching.py`,
  `scripts/fill_zones.js`, `scripts/fill_zones.py`, `scripts/embed_fonts.js`,
  `scripts/embed_fonts.py`, `scripts/check_zone_fills.js`,
  `scripts/check_zone_fills.py`, `scripts/drc_rules.js`,

  through pcbnew and reflows the file; a step that assumes a predecessor
  already ran; an error path that logs and continues, leaving a
  half-processed board that later steps treat as good; a write that reaches

- **Derived artifacts and manufacturing outputs** —
  `scripts/generate_jlcpcb_files.js`, `scripts/generate_layout.js`,
  `scripts/convert_jscad.js`, `scripts/convert_svg_to_footprint.js`, the

  `.github/workflows/check.yml`, `docs/bom.md`, `docs/build-guide.md`,
  `README.md`, `pcbs/temporal/README.md`. These turn the source of truth into
  things a manufacturer or a user consumes, and a mistake here ships as a
  wrong physical object. What goes wrong: coordinate and rotation math;
  mirroring and left/right derivation; a mapping table that has drifted from
  `points.zones`; documented quantities that no longer match the generated
  BOM.

- **Locally patched vendored footprints** —
  `ergogen/footprints/ceoloide/switch_choc_v1_v2.js`, `mcu_nice_nano.js`,
  `display_nice_view.js`, `battery_connector_jst_ph_2.js`,
  `power_switch_smd_side.js`, `reset_switch_smd_side.js`,
  `rotary_encoder_ec11_ec12.js`, `diode_tht_sod123.js`,
  `mounting_hole_npth.js`, `utility_text.js`. Vendored from ceoloide's library
  and patched locally for traces, vias, jumper resistor pads, Choc v2 support,
  KiCad 10 compatibility, and the `label_font_face` / `label_font_thickness`
  parameters that `power_switch_smd_side.js` and `mcu_nice_nano.js` accept.
  CLAUDE.md says to diff against upstream rather than replacing these
  wholesale. What goes wrong: a patch applied to only one of the `reversible`
  code paths, so the left and right hands differ; pad or net names that no
  longer line up with the `column_net` / `row_net` values the config passes
  in; geometry added without a matching clearance, which only DRC on a board
  that actually uses that parameter combination would catch.

For each sub-agent, provide:
- The full list of files in its area, not a diff.
- The scope description from the user, if any, so it knows what to focus on.
- The review criteria below that apply to its area, plus the core invariants,
  which apply everywhere.

Tell sub-agents to read entire files rather than scanning for patterns.
Finding a real issue requires the surrounding context. Where a package
documents its own contract, hold the code to that contract.

### Priority tiers

Tier by consequence, not by category. The categories under each tier are
examples, not the definition.

**Tier 1 (must fix):** produces behavior a user or the data can observe as
wrong, or violates a core invariant. Bugs, races, corrupt or non-atomic
writes, swallowed errors that hide a failure, layer violations.

**Tier 2 (should fix):** correct today, but the next change in this area is
likely to break it, or a real invariant has no test. Significant duplication,
resource leaks, API shapes that invite misuse, meaningful refactors.

**Tier 3 (consider):** removes something concrete. If you cannot name what it
removes, leave it out.

### The finding gate

Every finding must name its failure scenario: the input, call sequence, or
state that produces the wrong outcome. "This could race" is not a finding.
"Two concurrent writes both read before either writes, so the second save
clobbers the first" is.

A finding that cannot name a trigger is dropped, not downgraded. Report file
and line, what goes wrong, and a fix specific enough to act on.

In a hardware repo the observable wrong outcome is usually physical: a board
that will not assemble, a case that will not fit, a gerber that a fab will
reject, a BOM that orders the wrong count. Prefer findings you can tie to one
of those.

### Review criteria

**Core invariants (hard rules, violations are Tier 1)**

These are the contracts the whole build rests on. See `CLAUDE.md`, the header
comment of `ergogen/config.yaml` (lines 1-13), `pcbs/temporal/README.md`, and
the module docstrings of `scripts/drc_rules.js` (lines 2-7),
`scripts/kicad_config.js` (2-5), `scripts/ergogen_config.js` (2-5),
`scripts/fix_silkscreen_width.js` (2-12) and `scripts/embed_fonts.py` (2-19).

1. **`ergogen/config.yaml` is the only place geometry is authored.** Every
   dimension, offset, and outline in a shipped artifact traces back to it;
   generated `.kicad_pcb`, `.jscad`, and `.stl` files are never hand-edited to
   change geometry. `units:` (lines 24-152) holds every tuning constant by
   name, so a dimension change is a one-line edit at the top.
   *Violation shape:* a numeric literal in a `scripts/*.js` or `*.py` body
   that determines board or case geometry rather than KiCad's file format; an
   `outlines:` / `cases:` entry repeating a value that a `units:` name already
   holds, so the "one-line edit at the top" promise no longer holds.
   *Check:* grep the scripts for bare decimal literals and classify each as
   format constant or geometry. The known borderline cases are
   `add_ground_planes.js:65` and `:262` (a 2.0 mm zone margin, passed as a
   default and repeated at the call site) and `fix_edge_cuts.js:14`
   (`MIN_SEGMENT_LENGTH`); confirm whether any *new* ones have appeared.

2. **The post-processing order in `Makefile:96-106` is load-bearing.** Each
   step mutates the `.kicad_pcb` files in place and assumes its predecessors
   ran. Specifically: `fix_silkscreen_width.js` parses Ergogen's single-line
   s-expressions, so it must stay ahead of every step that saves through
   pcbnew and reflows the file; `create_text_keepouts.js` must precede the
   pour; via stitching must precede zone filling, because placing vias
   invalidates existing fills; a board's `.kicad_dru` must exist before
   anything fills its zones, because the zone filler honours those rules; and
   `copy_pcb_if_missing.sh` must run after all of it, because whatever it
   copies is what `pcbs/` keeps.
   *Violation shape:* a call to `fill_zones.py` or `pcbnew.ZONE_FILLER`
   reachable without `writeDrcRules` having run for that board; a text-level
   regex edit inserted after `add_ground_planes.js`; a new step inserted into
   `Makefile:96-106` outside its dependency position; a derived board written
   with fills copied from a source whose rules differ.
   *Check:* `scripts/fill_zones.js:49-57` (rules written per board, then
   filled); `scripts/drc_rules.js:39-55`;
   `scripts/create_stealth_variants.js:176`;
   `scripts/setup_kicad_project.js:423`; the step ordering in
   `Makefile:96-106`.

3. **`pcbs/temporal/temporal.kicad_pcb` is never overwritten by the build.**
   It is hand-routed in KiCad and the manual routing cannot be regenerated.
   Only its `.kicad_pro` and `.kicad_dru` are rewritten.
   *Violation shape:* any write to `pcbs/temporal/temporal.kicad_pcb` without
   an existence guard; a `pcbs/**` glob that copies Ergogen output over it; a
   clean target that removes the directory; a `pcbnew.SaveBoard` reachable
   with a path under `pcbs/`.
   *Check:* `scripts/copy_pcb_if_missing.sh:29` (the `[ ! -f ]` guard) and
   `Makefile:229` (the `! -name temporal` exclusion in `clean`). Then grep
   every script for writes whose path can resolve under `pcbs/temporal/`.
   Note that `check_zone_fills.py` deliberately refills in memory and writes
   nothing back (`:9-13`, `:62-64`); confirm that is still true.

4. **Naming encodes generation and handedness.** A leading `_` marks an
   Ergogen-internal name that is never exported. `_left` is generated
   directly; `_m_right` is the mirror source that `convert_jscad.js` renames
   and mirrors into `<name>_right.stl`. The `_m_right` suffix never survives
   into `cases/`. Variants encode key count (`38` breakoff pinky, `42` full
   pinky) plus option suffixes (`socket`/`solder`, `kickstand`, `stealth`).
   *Violation shape:* a file in `cases/` matching `*_m_right*`; an exported
   `cases:` key beginning with `_`; an `_m_right` case with no `_left`
   counterpart, or one whose parameters differ beyond the mirror.
   *Check:* `ls cases/ | grep _m_right` must return nothing;
   `scripts/convert_jscad.js:66-75` (the rename) and `:117` (the mirror); pair
   every `_left` against its `_m_right` in the `cases:` section of
   `ergogen/config.yaml` (lines 1149-1437).

5. **`scripts/kicad_config.yaml` owns the tuning values, and
   `scripts/kicad_config.js` plus `scripts/ergogen_config.js` are the only
   readers of the two config files.** The YAML owns net classes, design rules,
   custom DRC rules, zone and via-stitching parameters, keepout text patterns,
   and the JLCPCB part numbers plus embedded-resistor positions. Adding an
   assembly part or changing a trace width is a config edit, not a code edit.
   `kicad_config.js:21-40` fills the net class track and via geometry in from
   `ergogen/config.yaml`'s `copper_*` units, so those numbers are typed once;
   `ergogen_config.js:39-82` supplies `pcbNames()` and `ergogenOutputPcbs()`,
   so no script repeats the board list or the "has the build run" preamble.
   *Violation shape:* any of those categories appearing as a literal in a
   `.js` or `.py` body; a script calling `yaml.load` on either config path
   directly instead of going through the two modules; a hardcoded board list;
   a `?? <literal>` fallback in a script that disagrees with the value the
   YAML actually sets, so the YAML looks authoritative while the code silently
   wins.
   *Check:* `grep -rn "yaml.load" scripts/` should return only
   `kicad_config.js:53`, `ergogen_config.js:27`, and `generate_layout.js:42`
   (which parses Ergogen's `points.yaml` output, not a config file). Then take
   every `??` in `scripts/setup_kicad_project.js:302-385` against the
   corresponding key in `scripts/kicad_config.yaml`; the known disagreements
   are `silk_line_width ?? 0.1` (`:381`), `silk_text_thickness ?? 0.1`
   (`:384`) and `min_text_thickness ?? 0.08` (`:371`) against the YAML's
   `0.16`, `0.16` and `0.153`. The remaining hardcoded list is
   `LAYERS_TO_PROCESS` at `scripts/create_text_keepouts.js:16`, mirrored by
   `SILKSCREEN_LAYERS` at `fix_silkscreen_width.js:17` and
   `create_stealth_variants.js:16`.

6. **Every side-bearing footprint on `pcbs.temporal` is `reversible: true`.**
   The board is reversible: one PCB serves as the left hand or, flipped, the
   right. A footprint that renders on only one side breaks one hand, and
   `generate_jlcpcb_files.js:298-311` rejects the build outright if an
   assembly part is not on the top copper layer, because the two CPL files
   differ by rotation alone.
   *Violation shape:* a footprint entry under `pcbs.temporal.footprints` in
   `ergogen/config.yaml` that declares a side but omits `reversible: true`; a
   patched footprint whose `reversible` branch places pads, traces, or vias
   that its non-reversible branch does not, or vice versa.
   *Check:* every `what: ceoloide/...` under `pcbs.temporal` (lines 1439-1635)
   either sets `reversible: true` or is `mounting_hole_npth`, which has no
   side. Ten reversible footprints and eight mounting holes is the current
   state.

7. **The KiCad 10 compatibility shims stay in place.** The installed toolchain
   is KiCad 10, while the ViaStitching plugin and parts of the pcbnew API
   assume KiCad 9 or earlier. Four shims exist and each has a comment saying
   why.
   *Violation shape:* a shim removed or bypassed; a new `pcbnew` call written
   against a pre-10 signature; a version comparison that compares the version
   string lexicographically, which sorts `"10.0.5"` below `"7"`.
   *Check:* `scripts/via_stitching.py:38-49` (the `GetBoardPolygonOutlines`
   arity shim), `:51-87` (the `_ComparableVersion` shim),
   `scripts/create_text_keepouts.py:131-135` (the `SetDoNotAllowZoneFills` /
   `SetDoNotAllowCopperPour` rename), and the two `sed` patches to
   `FillArea.py` at `Makefile:69-70`, whose application is verified at
   `Makefile:71-79`.

8. **Silkscreen is uniform, and every board carries its own fonts.** One face
   (`"Maple Mono NF"`), no bold, and every stroke at `units.silk_line_width`
   (`ergogen/config.yaml:62`, currently 0.16mm, above JLCPCB's 0.153mm
   minimum). KiCad addresses fonts by family plus bold/italic and every Maple
   Mono file reports `Maple Mono NF` as its first fontconfig family, so a
   weight-suffixed name like `"Maple Mono NF ExtraBold"` resolves to nothing
   and is silently substituted at export. Because the fonts are embedded,
   what gets fabricated does not depend on the exporting machine.
   *Violation shape:* a `face:` or `label_font_face:` value that is not
   exactly `"Maple Mono NF"`; a `bold` attribute on silkscreen text; a text
   `thickness` or `label_font_thickness` that is a literal rather than
   `silk_line_width`; a step ordered after `embed_fonts.js` that saves the
   board and drops `(embedded_fonts yes)`; a stealth variant that strips text
   but leaves megabytes of unused embedded typeface behind.
   *Check:* the four `face:` / `label_font_face:` sites at
   `ergogen/config.yaml:1502`, `:1538`, `:1574` and `:1587`, and the
   `thickness` sites at `:1504`, `:1539`, `:1575` and `:1588`;
   `scripts/fix_silkscreen_width.js:22-43` (widening, silkscreen layers only);
   `scripts/embed_fonts.py:49-65` (the `embedded_fonts` flag) and `:68-90`;
   `scripts/create_stealth_variants.js:100-130` (dropping the fonts once no
   text names a face). `make check` already decides whether a board that names
   a face embeds a font (`Makefile:190-202`), so do not restate that as a
   prose finding.

**Duplication and extraction**

- Repeated blocks (5 or more lines, similar structure) across files that
  should be a shared helper. Tier 2.
- Ignore trivial similarity: both call the same stdlib helper, both have an
  error check. Only flag duplication where extracting it measurably reduces
  the bug surface or eases a likely change.

Two rounds of extraction have already happened here: `kicad_config.js` and
`ergogen_config.js` replaced five hand-rolled YAML loaders and four copies of
the "does `ergogen/output/pcbs` exist" preamble, and `parseFootprints`
replaced two copies of the footprint parser. What remains is the
JS-wrapper-around-KiCad-Python shape: `create_text_keepouts.js`,
`fill_zones.js`, `via_stitching.js`, `embed_fonts.js` and
`check_zone_fills.js` each resolve the interpreter, quote-join an argv, run
`execSync`, parse the result, and report counts. Assess whether one helper

**Refactoring opportunities**

- Code that grew incrementally and would benefit from restructuring now that
  its shape is clear: a function doing three things that should be three; a
  type that accumulated responsibilities; data flow that got indirect when a
  simpler path exists. Tier 2.
- Every suggestion must name a concrete improvement. It **removes** something
  (an indirection, a duplicated pattern, a coordination point, a way for two
  things to get out of sync), **enables** something (makes X testable,
  unblocks a use case, lets a change land in one place instead of N), or
  **generalizes meaningfully** (one shape replaces N near-duplicate variants).
  "Same behavior, different shape" does not qualify, however elegant. If you
  cannot name what improved, leave it out.

**Test quality (assess each suite as a whole, not test by test)**

This repo has no test suite and no test framework, and for most of it that is
the right call: the verification that matters is DRC on the generated boards
and a visual check in a slicer. `make check` (`Makefile:174-221`) is the
harness, and a new mechanical check belongs there rather than in a unit test
runner. Do not propose a test framework for the KiCad-mutating scripts.

Do assess the coverage gap between what `make check` decides and what only
judgment currently catches, and propose at most one new check where the payoff
is clear. The uncovered logic that carries real risk: the coordinate and
rotation math in `generate_jlcpcb_files.js:87-101` and `:246-271`, the mirror
math in `generate_layout.js:173-188`, the arc-extreme math in
`add_ground_planes.js:27-59`, and the s-expression block extraction in
`create_stealth_variants.js:22-46`. Also uncovered: nothing regenerates or
diffs the committed gerber zips, so `gerbers/` can silently fall behind
`pcbs/`, and nothing asserts that a value the YAML owns has not been
duplicated as a literal elsewhere.

- Significant production behavior with no test at all, especially the core
  invariants above and every branch of the logic named under Correctness.
  Tier 2.
- Clusters of overlapping tests that could consolidate into fewer, clearer
  cases. Tier 2.
- Tests asserting implementation details (internal call order, private
  fields) instead of observable behavior. They break on refactor for no
  value. Tier 2.
- Duplicated test setup or helpers that could be shared. Tier 2.
- Weak assertions (a count checked but not the values, the wrong field
  asserted). Tier 2 only where the weakness could mask a real bug.
- Do not suggest tests for trivial edge cases, for every possible nil input,
  or splitting working tests for purity. Fewer, stronger tests beat many
  fragile ones.

**JavaScript idioms**

`eslint.config.js` enables exactly two rules, `no-unused-vars` (with
`args: 'none'` and `caughtErrors: 'all'`) and `no-undef`, over `scripts/` and
`ergogen/footprints/`. Both are decided by `npm run lint` in `make check`, so
unused bindings and undefined references are never findings. Everything below
is what no configured rule decides.

- Regex parsing of KiCad s-expressions is the dominant pattern and the
  dominant risk. Where a script already has access to KiCad's Python API,
  check whether the regex path exists for a reason (staying ahead of a pcbnew
  reflow, as `fix_silkscreen_width.js` documents) or is just older.
- `require` is used throughout with CommonJS; `package.json` declares no
  `type` and `eslint.config.js:8` sets `sourceType: 'commonjs'`. Flag any file

- The scripts disagree about whether a failure is fatal; see the Write

**Python idioms**

## Step 5: Verify and widen

For every finding from an area agent or from the cross-cutting analysis:

1. **Verify it yourself.** Read the file and line. Confirm the trigger is
   real. Drop anything speculative, cosmetic, or already handled elsewhere.
2. **Widen it.** Grep or glob for the same pattern across the whole
   codebase and report every occurrence, not just the one an agent happened
   to open.
3. **Mechanize what widens.** If a class has many instances and a tool could
   decide it, report one automation proposal instead of N findings: enable the
   lint rule, add the check, add a guard test. Check the lint configuration
   first, since a rule that exists but is disabled or not wired into CI is
   the cheapest fix available.
4. **Drop non-actionable observations.** Anything amounting to "noting this
   but it is fine" comes out.
5. **Deduplicate.** Merge findings that different agents reached from
   different angles into one item.

On step 3, note where this repo already stands. `make check` runs in CI on
every push and decides parsing, linting, the config build, DRC at error
severity, font resolution and embedding, zone-fill currency, and the
reproducibility of `temporal.json` and `jlcpcb/`. `eslint.config.js` has
`no-unused-vars` and `no-undef` on; enabling ESLint's recommended set on top
of them currently produces no additional errors, so proposing it would
subsume nothing. That means a new automation here almost always belongs as a
step in the `check` target rather than as a lint rule. The gaps that a
mechanical check could close: the committed gerber zips are never regenerated
or diffed against `pcbs/`, so they can fall behind silently; and no check
asserts that a dimension the YAML owns has not been re-typed as a literal in
a script or a doc. Propose these only if the findings actually justify them,
and say how many findings each subsumes.

## Step 6: Report

Present the report and stop. Do not fix anything, do not write findings to
memory, and do not leave a findings file behind: the human triages in the
session, and saved findings become confidently wrong context later.

Organize by tier, then by category within a tier. Within a tier, order by
value against effort.

Each finding gets:
- File path and line numbers
- The failure scenario: what goes wrong and what triggers it
- A fix specific enough to act on
- One entry per pattern, with all occurrences grouped under it

**Test quality findings** are a cohesive assessment per area, not a list of
files. "The syncer tests cover classify and dedup well but nothing exercises
the expired-session abort" beats "syncer_test.go:42: missing test".

**Refactor findings** include a sketch of the target structure, or at minimum
name the functions and types that would result.

**Automation proposals** name the rule or check, the config file it goes in,
and roughly how many current findings it subsumes.

An area with no findings says so. A short report on sound code is a successful
audit, not a lazy one. No nits, no cosmetic notes, no "just flagging this".
